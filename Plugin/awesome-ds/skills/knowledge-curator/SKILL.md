# knowledge-curator

Works in any language. Entries are written in Japanese (the Knowledge base language) with English titles kept as they appear at the source. If the user writes English, answer in English but still write the entry in Japanese unless told otherwise.

You maintain three things in this repository: `Knowledge/**` (entries), `Reference/REFERENCE.md` (the index), and proposals to `AwesomeDS/` (the canonical DS) with `CHANGELOG.md`. You never edit `AwesomeDS/` directly on the main branch; you propose changes as a PR with a CHANGELOG bump. The plugin copy under `Plugin/awesome-ds/ds/` is regenerated by `Plugin/awesome-ds/scripts/sync-ds.sh`, never edited by hand.

Mode: if `$ARGUMENTS` is `weekly`, run section 4. Otherwise treat `$ARGUMENTS` as a URL or topic and run sections 1 to 3.

## 1. Research the source

1. Fetch the primary source (WebFetch). Read release notes, docs pages or the repository README. Do not rely on memory for versions, dates, or API names. If a fact cannot be verified from a fetched page, leave it out.
2. Collect: exact name, current version and release date, licence, what changed, concrete values (sizes, durations, colours, API names, defaults). Values are the point of an entry; opinions are not.
3. Check for an existing entry: `Grep` the title and URL across `Knowledge/**/*.md`. If one exists, update it (bump `updated`, add to sources, revise sections) instead of writing a duplicate.

## 2. Write the entry

Path: `Knowledge/<category>/<kebab-case-name>.md`. Categories are the existing folders under `Knowledge/`; list them with Glob before choosing. Create a new category only when nothing fits, and add it to REFERENCE.md.

Frontmatter, exactly this shape (keys in this order, `updated` is today's date):

```
---
title: "<name>"
category: <folder>
type: <repo | library | skill | article | product | guideline | design-system>
sources:
  - url: <https://...>
    title: "<title>"
tags: [..]
updated: YYYY-MM-DD
---
```

Body sections, in this order, all five present (write "該当なし" when a section is empty):

```
## 概要
2 to 4 sentences: what it is, who makes it, why it matters for UI built by agents.

## 要点
Bullets. Each bullet is one fact with a number, a name or a rule. No adjectives without evidence.

## 具体的な値・ルール
Table or code block of the exact values: tokens, sizes, durations, API signatures, defaults, install command. This section must be copy-pastable.

## AwesomeDS への反映
One of: "反映済み (AwesomeDS x.y.z, <file>)", "提案: <one-line change> → <AwesomeDS file and section>", or "反映不要: <reason>". Every proposal here must appear in section 3.

## 出典
Numbered list of the URLs fetched, with the date fetched.
```

Template with placeholders: `${CLAUDE_PLUGIN_ROOT}/skills/knowledge-curator/templates/entry.template.md`.

Rules

- `title` is the official name, not a description. `tags` are lowercase kebab-case, 3 to 8 of them, reusing existing tags first (Grep `^tags:` across Knowledge).
- No em dashes, no filler, no marketing adjectives copied from the source.
- Japanese body, English proper nouns and code as they are.
- One entry per subject. A release note for a library updates the library's entry; it is not a new entry.

## 3. Update the index and propose DS changes

1. `Reference/REFERENCE.md`: add or update the row for the entry in its category table: `| [title](../Knowledge/<category>/<file>.md) | type | one-line summary | updated |`. Keep rows sorted by title within each category. If the file does not exist yet, create it with one table per category and a header explaining the format.
2. For every "提案" in the entry's `AwesomeDS への反映` section, write the change against `AwesomeDS/` (DESIGN.md frontmatter and rules, `tokens/tokens.css`, `tokens/tailwind.css`, `tokens/tokens.json`, `foundations/*.md`, `components/*.md`) keeping all four token files consistent.
3. `AwesomeDS/CHANGELOG.md` (create with a `# Changelog` header and Keep a Changelog sections if missing): add an entry under `## [Unreleased]` or a new version heading. Bump: patch for wording and source updates, minor for a new token or rule, major for a token rename or removal. Update `version:` in `DESIGN.md` frontmatter and the header comments in `tokens.css` and `tokens.json` to the same number.
4. Run `bash Plugin/awesome-ds/scripts/sync-ds.sh` so the plugin copy matches, then `bash Plugin/awesome-ds/scripts/check-sync.sh`.
5. Present the proposal as a PR description: title `ds: <change> (from <entry title>)`, body with the entry link, the diff summary, the CHANGELOG line, and the contrast script output when a colour changed (`node Plugin/awesome-ds/skills/ds-creator/scripts/contrast.mjs AwesomeDS/tokens/tokens.css`). Do not merge; the human decides. If you are not allowed to run git in this session, write the PR description to `Reference/proposals/<date>-<slug>.md` and say so.

## 4. Weekly routine (`weekly`)

Run on a schedule or when asked. Do all of it; do not stop after the first interesting release.

1. Check each source for changes since the last run (the `updated` field of its Knowledge entry, or the last 7 days when no entry exists):
   - shadcn/ui: https://ui.shadcn.com/docs/changelog and the GitHub releases.
   - Motion (`motion`, formerly Framer Motion): https://motion.dev/docs and GitHub releases.
   - Tailwind CSS: https://tailwindcss.com/blog and GitHub releases.
   - Radix Primitives and Radix Themes: GitHub releases. Base UI (MUI): https://base-ui.com releases.
   - Apple Human Interface Guidelines: https://developer.apple.com/design/whats-new/
   - Material Design 3: https://m3.material.io/blog and the material-web releases.
   - Geist and Noto Sans JP font releases (vercel/geist-font, notofonts).
   - Notable design system launches: search "design system launch" and "design tokens" news for the last 7 days (WebSearch), and the Design Systems Repo / design-systems.surf feeds.
2. For each change found, decide: no effect on AwesomeDS (record in the entry only), a value change (propose), or a rule change (propose). A new shadcn component that AwesomeDS's components/README.md does not cover is a rule change.
3. Write or update entries (section 2) for everything that changed. One entry per subject, updated in place.
4. Produce one PR proposal (section 3) bundling all DS changes for the week, with one CHANGELOG entry listing each change and its source entry.
5. Print a digest: `| source | version or date | change | effect on AwesomeDS | entry |`, then the PR proposal path or link. Nothing else.

## What you never do

- Invent a version, date or value you did not read on a fetched page.
- Edit `Plugin/awesome-ds/ds/` by hand.
- Write an entry without all five body sections and the exact frontmatter.
- Change AwesomeDS without a CHANGELOG line and a version bump.
- Merge your own proposal.
